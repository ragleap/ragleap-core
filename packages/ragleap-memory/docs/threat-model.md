# ragleap-memory 0.3.1: threat model

Status: fourth version. It covers only what 0.3.1 contains (row 16 is new). Anything not listed as defended is not defended. This library has had no independent security review.

## Scope of 0.3.1

New in 0.3.1: encrypted export and import files (export format version 2, `exportcrypto.py`), using the `crypto` module of ragleap-security 0.2.0. No schema change.

New in 0.3.0: optional vector and hybrid search over vectors that the caller's embedder function produces (`embed_pending`, `search(mode=...)`, schema 3). The library itself never contacts an embedding provider.

`SQLiteStore` and, new in 0.2.0, `ShardedStore` (one file per tenant), token budgets on search, usage counters and per-tenant quotas. `SQLiteStore`: durable memory in one SQLite file (or in memory) with FTS5 keyword search, typed entries with trust labels, supersession, per-scope export and erase, and an optional audit log. It uses `Scope`, `AuditLog` and the limits from ragleap-security 0.1.0. Nothing in `core/` or ragleap-rag uses it yet. In the table, "What 0.1.0 does" is what the library does, unchanged in 0.2.0 unless a row says otherwise.

## Threats

| # | Threat | What the library does | Backed by | Not defended |
|---|--------|-----------------|-----------|--------------|
| 1 | One tenant reads, changes or deletes another tenant's entries | Every operation requires an exact `Scope`. The scope is applied inside the SQL (tenant plus any narrower subject, agent and session). `derived_from` ids must be visible to the writer's scope. A missing entry and an invisible entry give the same error. | `tests/test_isolation.py`, `tests/test_add_validation.py`, `tests/test_lifecycle.py`; 11 mutations in `scripts/mutation_check.py` | The caller chooses the scope. The store cannot know whether a caller is entitled to it: authentication and mapping users to scopes belong to the application. Anyone who can read the database file or hold the store object bypasses it. A tenant-wide scope sees everything in its tenant by design. |
| 2 | Untrusted or poisoned text is later treated as trustworthy | Every entry carries a trust label (`untrusted`, `model`, `owner`); the default is the lowest; `min_trust` filters searches; derived entries record their sources. | `tests/test_search.py`, `tests/test_add_validation.py`; 2 mutations | Labels are only as honest as whoever writes them: a writer can claim `owner`. The store does not stop a consumer from putting retrieved text into a prompt as instructions. Defending against prompt injection through retrieved memory is the consumer's job (the ragleap-agents integration is planned). No content scanning. |
| 3 | A search query changes the query, or is used to exhaust resources | Queries are reduced to quoted words joined with OR, so operators are plain words; at most 32 words and 1,000 bytes; results are capped (default 50). | `tests/test_search.py`, `tests/test_isolation.py`; 3 mutations | A slow query inside these limits on a very large store. No timing has been measured. |
| 4 | Deleted text stays in the database file | `erase()` deletes, rewrites the full-text index, and checkpoints the journal; `secure_delete` is turned on explicitly. A byte-level test checks the text is gone from the file. Since 0.3.0 the entry's vector is deleted with it (a database trigger) and a second byte-level test checks the vector bytes are gone too. | `tests/test_lifecycle.py`; 2 mutations | `forget()` leaves traces in the search index until `compact()` or `erase()` runs (a test pins this). Other SQLite builds, other operating systems, file system journals, SSD wear levelling, backups, snapshots and copies of the file are **not verified**. |
| 5 | A change happens without a record, or half-happens | The optional `AuditLog` is written inside the transaction, so a failing audit write rolls the change back; the log holds ids and counts, never entry text; any error rolls the whole write back. | `tests/test_durability.py`; 2 mutations | The audit log is optional and off by default. Reads (`get`, `search`, `count`) are not audited, only `export`. The log is tamper-evident, not tamper-proof (see the ragleap-security threat model). |
| 6 | Oversized input exhausts memory or disk | Text is capped at 8,192 bytes; metadata at 4,096 bytes, depth 8 and 1,000 values; `derived_from` at 100 ids; `forget` at 1,000 ids. | `tests/test_add_validation.py`; 2 mutations | Quotas (0.2.0) are off by default and count entries and *estimated* tokens, not bytes on disk or metadata. No cap on the file size and no rate limiting. |
| 7 | The database file is readable by other local users | The file is created with mode 0600. Checked by hand on Linux, SQLite's `-wal` and `-shm` files were 0600 too; the test checks only the main file. | `tests/test_durability.py`; 1 mutation | A file that already exists keeps its permissions. No encryption at rest (planned with ragleap-security `crypto`, not in 0.1.0). Backups. |
| 8 | A newer schema is opened by older code, or writers collide | A database with a newer schema version is refused; a 0.1.0 or 0.2.0 file is migrated to schema 3 in one transaction, so a crash leaves the old schema or the complete new one (a migrated file cannot be opened by older versions); writes run in `BEGIN IMMEDIATE` transactions with WAL; threads share one locked connection. | `tests/test_durability.py` (8 threads, 200 writes), `tests/test_embed_storage.py` (a 0.2.0 file migrates, a schema-3 file reopens unchanged); 4 mutations | Several processes writing the same file, network file systems and power-loss durability beyond SQLite's defaults are **not verified**. |
| 9 | An outdated or expired fact is used as if current | Expired and superseded entries are hidden from search unless asked; `supersede` links the new entry to the old one and refuses a second supersession. | `tests/test_search.py`, `tests/test_lifecycle.py`; 3 mutations | The store cannot know a fact is wrong. Two contradicting entries added with `add()` both stay current. |
| 10 | A tenant, or a bug, makes the memory cost grow without limit: a bill spike from long prompts, or storage that grows forever | `search(max_tokens=...)` returns at most that many estimated tokens whatever the store size. `quota_entries` and `quota_tokens` refuse writes past a per-tenant limit; usage counters show what was stored and served per day. | `tests/test_tokens.py`, `tests/test_usage_quota.py`; 21 mutations | Token counts are estimates (3 bytes per token), not a real tokenizer, so an exact bill is not predicted. The budget bounds tokens, not time. Quotas are off unless set. What your application sends to a model (system prompts, other context) is outside this library. Nothing bills or alerts anyone. |
| 11 | One large tenant slows down or exposes the others through a shared index or file | `ShardedStore` gives each tenant its own file, index and quota; file names are a hash of the tenant id, never the id; tenant ids cannot contain path characters; a tenant-wide `erase` deletes the files. | `tests/test_sharded.py`; 8 mutations | Same host, same directory and same process: a bug in the application or in the library can still cross tenants, and anyone who can read the directory can read every tenant. Not stronger than the scope filter in security terms. Performance gain is measured only on synthetic data (see CHANGELOG). Many tenants mean many files: `max_open` bounds open files, not disk. |
| 12 | An uploaded memory file is hostile: it claims `owner` trust, writes into another tenant, is huge, truncated or malformed, or smuggles links to other entries | Import is strict and all-or-nothing: entries are checked like `add`; trust is capped at `max_trust` (default `untrusted`); every entry must lie inside the import scope (`rescope` is an explicit opt-in); ids are always new and links are remapped or dropped; limits on entries, bytes and line length; a header with a version and an entry count detects truncation; duplicates are skipped. Error messages hold line numbers, never text. | `tests/test_portability.py`; 28 mutations | The text of an imported entry is still *data from an unknown source*: it can contain prompt-injection text, and `untrusted` only labels it, the application must treat it so. Import cannot tell who is allowed to upload: authorisation is the application's job. A file can fill a tenant up to its quota. A plain export file is not encrypted (row 16 covers the encrypted format), and a copy of it outside the library is not tracked. Entries from a trusted source imported with a high `max_trust` are trusted by that choice. |
| 13 | A tenant, or a bug, makes embedding cost grow without limit: a bill from an embedding provider | The library has no provider code and no keys; it only calls the function you pass. `embed_pending` embeds only entries without a vector, in batches of `embed_batch_size`. `embed_quota_tokens` (off by default) caps estimated embedder tokens per tenant per UTC day, checked and counted *before* each call (a call that then fails stays counted). When a batch would pass the cap only the entries that fit are embedded; if none fit, `QuotaExceededError` is raised before the embedder is called. A vector or hybrid query is one call and counts against the same cap. `dry_run` shows what would be sent. | `tests/test_embed_pending.py`, `tests/test_vector_search.py`, `tests/test_embed_sharded.py`; 22 mutations | Token counts are estimates (`token_estimator`), not what a provider bills. The cap is off by default and covers only calls made through this library. The texts are sent to *your* embedder and leave the process wherever it sends them. An embedder that never returns blocks the call: there is no timeout. |
| 14 | Vector search returns another tenant's entry, a hidden entry, or a leftover vector of deleted text | Vector and hybrid search use the same scope clause in SQL as keyword search; kinds, `min_trust`, superseded and expired entries are filtered in the same query; only vectors of the store's current model and size are compared. `embed_pending` embeds only entries the scope can see, so the embedder is never given another tenant's text. A vector is deleted with its entry (trigger), `erase` removes the vector bytes from the file (byte-level test), and export files carry no vectors. | `tests/test_embed_isolation.py`, `tests/test_embed_storage.py`, `tests/test_vector_search.py`; 22 mutations | Vectors are stored unencrypted in the SQLite file, like the text, and can reveal information about the text: anyone who can read the file can read them. `forget()` leaves traces until `compact()`, as for text. Similarity is not relevance: someone who can write untrusted entries can craft text that lands close to a chosen query, so trust labels and `min_trust` remain the defence. |
| 15 | A broken or hostile embedder, or a very large store, makes vector search return garbage, crash or run for too long | The embedder's result is checked before anything is stored: one vector per text, exactly `embedding_dim` finite numbers, not all zero. Anything else raises `EmbedderError` (the message never contains text or vectors) and stores nothing from that batch. Vectors are stored normalized; a damaged stored vector is skipped. One search scans at most `max_vector_candidates` entries (default 5,000, newest first) and returns at most `k`. | `tests/test_embed_pending.py`, `tests/test_vector_search.py`; 32 mutations | Vector search is exhaustive only up to the cap; older entries are not scanned in vector mode. Scan time grows with candidates times dimensions: about 128 ms for 10,000 vectors of 384 numbers and about 470 ms for 10,000 of 1,536 were measured once in a sandbox, not on the VPS. An embedder that returns plausible but wrong vectors cannot be detected. |
| 16 | An export file is read, copied or changed outside the library: a backup, a file in transit, a file someone swaps or edits | `export_file(..., encrypt_with=` a `Key` or `KeyRing`, or `passphrase=...)` writes format version 2: a plain JSON header and one AES-256-GCM envelope per entry, made by ragleap-security (no cryptography is implemented here). Each line is authenticated together with a fixed label, the SHA-256 of the exact header line, its own position and the caller's `context`, so a wrong key, a wrong context, any changed byte, and a line that is moved, duplicated or taken from another file all fail with `line N: cannot decrypt`; dropped or extra lines fail the entry count. Only canonical base64 and exactly one newline per line are accepted. A passphrase is stretched once per file (scrypt), and the header's scrypt settings are range-checked before any work. An encrypted file is refused without a key or passphrase, and a plain file is refused when one is given, so a plain file cannot be swapped in. After decrypting, the normal import runs unchanged (trust cap, scope check, quotas, one transaction, limits); an encrypted line may be 90,000 bytes and the file on disk twice `max_bytes`; the entry count in the header is checked against `max_entries` before anything is decrypted. Messages hold line numbers, never text, keys or passphrases; the audit events say `encrypted: true` and nothing more. | `tests/test_export_crypto.py`, `tests/test_export_crypto_optional.py`; 55 mutations | It protects the export FILE only: the SQLite database is still unencrypted at rest, and so is process memory while exporting or importing. The header shows the number of entries and line lengths show roughly how long each entry is. Anyone who holds the key can read and forge a file. An old file put back in place of a newer one is not noticed (no freshness). The header of an empty export is not authenticated (nothing to protect). A decrypted file is still untrusted input. The key itself is the application's to store and rotate. Not reviewed independently. |

## Not covered in 0.3.1

Encryption of the database file at rest, a faster or approximate vector index, consolidation, retention and decay beyond expiry, importance-based ranking (importance is stored but does not affect ranking yet), Postgres, a review queue, and the ragleap-agents adapter. Retrieval quality has not been measured on any benchmark.

Languages: search uses SQLite's `unicode61` tokenizer. Whole-word search is tested for Hindi, Tamil, Arabic and Chinese written with spaces. Chinese or Japanese text without spaces is not split into words. Words in Indic scripts are split at combining marks, so partial matches can be loose; precision has not been measured.

## How this document is checked

`python scripts/mutation_check.py` breaks one protection at a time in a temporary copy and requires a test to fail. All 232 listed mutations were killed when this version was written (Python 3.12.3 and Python 3.10.20 in the author's sandbox; the VPS run is recorded in the release notes). A killed mutation shows a protection is exercised by a test; it does not show the protection is sufficient.

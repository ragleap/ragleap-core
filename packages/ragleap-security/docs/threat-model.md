# ragleap-security 0.2.0: threat model

Status: second version. It covers only what 0.1.0 and 0.2.0 contain. Anything not listed as defended is not defended. This library has had no independent security review.

## Scope of 0.2.0

Eight modules. From 0.1.0: `scope` (tenant scopes), `audit` (hash-chained log), `secrets` (secret wrapper and redaction), `limits` (input limits). New in 0.2.0 (design: #1237): `keys` (a key that does not print itself, and a ring for rotation), `crypto` (AES-256-GCM, needs the optional `cryptography` package), `ratelimit` (token buckets) and `integrity` (file manifests). Everything except `crypto` is standard library only. No store uses these yet; ragleap-memory (#900) is the first planned consumer.

## Threats

| # | Threat | What this library does | Backed by | Not defended |
|---|--------|-----------------|-----------|--------------|
| 1 | One tenant reads or writes another tenant's data because a scope is missing, forged or ambiguous | `Scope` is immutable and validated; `key` is unambiguous; `covers` and `require_scope` accept only an exact `Scope` (no strings, dicts or subclasses) | `tests/test_scope.py`; 7 mutations in `scripts/mutation_check.py` | A store that never calls `require_scope`, or never filters by scope, is not protected. No store exists yet, so tenant isolation as a whole is **not verified**. |
| 2 | A secret is printed, logged, pickled or serialized by accident | `SecretStr` masks `str`, `repr`, `format` and f-strings, refuses pickle and JSON, is unhashable, compares in constant time; `from_env` reads by variable name and its errors never contain values; `redact` removes known values and common credential formats | `tests/test_secrets.py`; 9 mutations | Code that calls `reveal()` and logs the result. A secret in a format `redact` does not know (it is a heuristic with false negatives). Secrets in process memory, swap or core dumps. Other processes of the same user reading the environment. |
| 3 | Someone edits, deletes, reorders or inserts a record in the audit log | `verify()` detects it through sequence numbers, chain links and SHA-256 hashes; appends fail closed on a corrupt or incomplete log; the log file is created with mode 0600 (the lock file too, which is not mutation-checked) | `tests/test_audit.py`; 6 mutations | Cutting records off the END of the log is not detected unless you keep the last hash or count outside the log and pass it as an anchor. Someone who can rewrite the whole file and recompute every hash is not detected (the tests pin both limitations). Deleting the file. A trusted writer that records false events. Timestamps are not trusted. |
| 4 | A forged or malformed audit record (log injection) | Event names are restricted; records are single-line canonical JSON with ASCII escaping; size is capped at 65,536 bytes; `SecretStr` values are written as `[REDACTED]` | `tests/test_audit.py`; 2 mutations | Secrets that are not wrapped in `SecretStr` are written as given. Callers must not put secrets in audit data. |
| 5 | Hostile input exhausts memory or CPU | `check_size`, `check_json_shape` (iterative, so no recursion crash), `bounded_read`, cooperative `Deadline`; `redact` has a length cap and was timed on four hostile inputs | `tests/test_limits.py`, `tests/test_secrets.py`; 6 mutations | Limits only apply where a caller invokes them. `Deadline` does not interrupt running code. |
| 6 | Concurrent writers corrupt the audit chain | An in-process lock and, on POSIX, a file lock | Thread test (8 threads, 200 records) and process test (4 processes, 80 records) | Not mutation-checked (race tests are probabilistic). Windows multi-process, network filesystems and Python versions other than those tested are **not verified**. |
| 7 | Exported or stored data is read, or changed without notice, by someone who does not have the key | `crypto` encrypts with AES-256-GCM (through the `cryptography` package). Any change to the envelope, the key id, the context or the ciphertext makes decryption fail with one generic error. Keys have ids and a `KeyRing` supports rotation (`reencrypt`). A passphrase can be used instead of a key (scrypt, settings stored in the envelope and range-checked on read). | `tests/test_crypto.py`, `tests/test_keys.py`; 47 mutations | Data while the program runs and the key is in memory. Anyone who holds the key or the passphrase. A weak passphrase (only a floor of 8 characters is checked). What an envelope shows: its size, the key id and the scrypt settings. Replacing a file with an older valid envelope (there is no freshness check). Random 96-bit nonces: use each key for well under about 2^32 messages and rotate; this is documented and is not enforced across processes. The `cryptography` package and OpenSSL are trusted, not reviewed by us. Data over 64 MiB is refused (no streaming yet). |
| 8 | One tenant's encrypted data is presented as another tenant's | The context (bytes, a string or a `Scope`) is authenticated: decrypting with a different context fails. | `tests/test_crypto.py`; covered by the `crypto` mutations | Only works if the caller passes the right context every time; a store that leaves it out gets no protection. The context is not secret. |
| 9 | One client floods an entry point | `RateLimiter` is a token bucket per key with bounded memory. A new key is refused when the table is full of busy keys, so flooding with new keys cannot reset a throttled key. `SQLiteRateLimiter` shares the limit between processes on one machine. Both refuse when they cannot decide. | `tests/test_ratelimit.py`; 26 mutations | Attacks spread over many machines, or over keys you do not control (a limit is only as good as the key you choose; an IP address can be spoofed). The in-memory limiter forgets everything on restart. The SQLite limiter uses the wall clock (a clock set forward gives extra tokens), trusts the file's access rights, and is **not verified** on network filesystems. The SQLite transaction mode is not mutation-checked (the thread test is probabilistic). A limit does not detect abuse. |
| 10 | Files (code, configuration, model files) are changed after a manifest was made | `integrity` lists every file with its SHA-256 and reports changed, missing and extra files. With a `Key` the manifest carries an HMAC-SHA256, so changing the manifest is detected by anyone who holds the key. Symlinks and special files are refused and never followed; file count and size are limited. | `tests/test_integrity.py`; 32 mutations | An unsigned manifest that is changed together with the files. Anyone who holds the HMAC key. A change made between the check and the use of a file. Authorship: an HMAC with a shared key does not show who wrote the files (public-key signatures are not included). **Copying is neither prevented nor detected.** Windows is **not verified** (the no-symlink open flag is POSIX). |

## Not covered

Chunked (streaming) encryption for very large files, public-key signatures, canary tokens for detecting and tracing leaks (planned for 0.3.0; they would detect and trace, never prevent copying), an SSRF-safe HTTP helper, a policy engine, secret and PII detection for outputs, a red-team harness, prompt-injection defences (the taint rule lives in ragleap-agents), supply-chain controls, and independent review. These are planned in #899 and are not claimed here.

## How this document is checked

`python scripts/mutation_check.py` breaks one protection at a time in a temporary copy and requires a test to fail. All 135 listed mutations (30 from 0.1.0 and 105 added in 0.2.0) were killed when this version was written. A killed mutation shows the protection is exercised by a test; it does not show the protection is sufficient.
